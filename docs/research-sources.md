# Project CG Studio: smallest useful resin-pouring pipeline

Checked 2026-10-11 UTC. Read-only GitHub/API and official documentation research; no installation, repository-code execution, rendering, GPU benchmark, or asset export test was performed. Recommendations below are engineering judgments, not measured quality/performance claims.

## Recommendation

**Choose B, Blender Cycles, for the finished resin-pouring film.** Start with Blender, its bundled Python API, one reproducible scene-building/render script, and an image-sequence-to-video step. None of the six candidate repositories is mandatory for this one-shot production. Add a GPU worker only after an actual device/backend check and a representative frame benchmark. Preserve the currently running CPU render.

- **A. Traditional Three.js:** smallest browser stack is Three.js + its loaders/controls + MeshPhysicalMaterial + an HDR environment. Add React Three Fiber only if the surrounding app already benefits from React, and postprocessing only for specific effects. Good for an interactive product preview. Rasterized transmission is an approximation, especially for resin inside a transparent cup; bloom and grading cannot reconstruct missing optical paths. Current WebGLRenderer source builds the transmission buffer primarily from opaque objects, with a special double-sided backface pass, not arbitrary nested refractive transport. [Renderer source](https://github.com/mrdoob/three.js/blob/dev/src/renderers/WebGLRenderer.js#L2015-L2139), [material parameters](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)
- **B. Blender Cycles:** best fit for final frames with thick glass/resin, multiple refractive boundaries, controlled light transport, absorption, motion blur, and offline sampling. Build the cup as real walls with sensible normals, model the liquid/air boundary and meniscus deliberately, and light with large shapes that read clearly in reflections. Use an art-directed procedural pour for a controlled shot or a baked liquid simulation when flow behavior matters; neither an MCP server nor a render wrapper creates good fluid motion automatically. Blender's liquid settings explicitly include viscosity and surface tension. [Fluid modifier](https://docs.blender.org/manual/en/latest/modeling/modifiers/physics/fluid.html), [diffusion/viscosity](https://docs.blender.org/manual/sl/4.4/physics/fluid/type/domain/liquid/diffusion.html)
- **C. Blender GLB → Three.js:** useful when interactive delivery is required: author geometry/UVs in Blender, export supported PBR data, then rebuild the lighting and test the result in Three.js. This is an asset handoff, not transfer of a Cycles-rendered appearance. Maintain the .blend as master and a separate web look. A changing-topology liquid simulation is not a normal GLB animation: use a deliberately designed fixed-topology animation, a custom sequence/cache representation, or a pre-rendered film. Core glTF animation covers transforms, skinning and morph weights; newer animation-pointer extensions do not turn a fluid cache into a simulation. [Blender export support](https://docs.blender.org/manual/en/5.1/addons/import_export/scene_gltf2.html)

## What actually survives Blender → GLB

1. Principled Transmission Weight maps to **KHR_materials_transmission**; transmission texture uses its red channel. Transmission is separate from alpha coverage. In Three, keep opacity at 1 for a fully present transmissive solid. [Exporter](https://github.com/KhronosGroup/glTF-Blender-IO/blob/main/addons/io_scene_gltf2/blender/exp/material/extensions/transmission.py), [Three material](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)
2. **KHR_materials_ior** carries IOR, normally omitting the default 1.5 unless animation needs it. Exporter gates it on transmission, volume or specular extensions. Do not assume a named Blender Glass shader, arbitrary node graph or procedural texture is serialized faithfully. [IOR exporter](https://github.com/KhronosGroup/glTF-Blender-IO/blob/main/addons/io_scene_gltf2/blender/exp/material/extensions/ior.py)
3. **KHR_materials_volume** can carry absorption color, attenuation distance and thickness. Blender exporter reads Volume Absorption color, maps density to inverse attenuation distance, and requires the custom glTF Material Output **Thickness** socket with a nonzero value or a supported texture. Missing Thickness can omit the volume extension entirely. Texture thickness is green-channel data. [Volume exporter](https://github.com/KhronosGroup/glTF-Blender-IO/blob/main/addons/io_scene_gltf2/blender/exp/material/extensions/volume.py)
4. The volume extension describes a homogeneous medium bounded by a closed/manifold mesh. It does not define volumetric scattering. Rasterizer thickness is a lossy approximation; the specification says ray tracers should use actual traversed distance while retaining thicknessFactor's thin-wall/volume distinction. This is not Cycles node-graph parity. [Khronos volume specification](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_materials_volume/README.md)
5. Three's GLTFLoader maps these extensions into physical-material transmission, thickness, attenuation and IOR values. Successful loading proves parameter import, not identical rendering. Lighting, world shaders, compositing, complex procedural nodes and fluid caches need separate treatment. Inspect exported JSON extensions and compare one controlled frame in both renderers before committing to the hybrid route. [GLTFLoader](https://github.com/mrdoob/three.js/blob/dev/examples/jsm/loaders/GLTFLoader.js)

## Hardware and validation gate

Cycles supports CPU rendering and GPU backends depending on hardware/OS, including NVIDIA CUDA/OptiX, AMD HIP, Intel oneAPI and Apple Metal. VRAM and drivers matter; CPU performance is a time constraint, not permission to substitute software WebGL and call it equivalent. GPU memory exhaustion can cause fallback or failure/performance penalties. Exact device support must be checked against the Blender version chosen. [Official GPU rendering manual, retrieved through search](https://docs.blender.org/manual/id/5.0/render/cycles/gpu_rendering.html)

Before expanding this stack: lock versions, verify the actual GPU/backend, render a representative middle-of-pour frame, inspect glass/resin interfaces and bubbles at full size, then render a short motion sample to check temporal noise and fluid continuity. Measure seconds per frame and projected total. Approve that look before full resolution/frame-count scaling. These checks are proposed, not performed.
